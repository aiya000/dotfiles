# 記事の型（構成テンプレート）

aiya000 の記事は、内容によって5つの型に分かれる。
書き始める前にどれか一つを選び、その型の見出し構成をベースにする。
見出し名は例なので、内容に合わせて言い換えてよい。ただし**結論が先**という順序は崩さない。

- - -

## 型A: 小ネタ・Tips（30〜100行）

一つの発見・ハマりどころ・小さな設計判断を共有する。
例: `$ echo '-eq'` の話、composables の `$` プリフィックス、`x as { foo?: T }` イディオム、Nuxt3 の emit の型、git-worktree と eslint。

````markdown
# 【タグ】一文で言い切るタイトル（〜する / 〜になる / 〜んだが）

## 結論

一文で状況説明。「単純だけど、そういうことです。」「下記のような感じ。」

```lang:file
（コピペで使えるコード。コメントで要点を指す）
```

- 実際に動く環境: https://stackblitz.com/...   （あれば）

## なぜそうなるのか / 解説

「解説する必要もないくらい単純なものですが、一応解説させていただきます :)」
悪い例 → 良い例。理由は型・仕様・ドキュメントへのリンクで1〜2文。

## おまけ / 余談（任意）

きっかけ・関連する自作ツール・「需要あるのか？」

## おわり

おわり。
（または一行の叫びで終える）
````

- 崩しの一行を2〜3回入れてよい。この型が一番くだけている
- 一人称は「僕」、です・ます
- **設定ファイル紹介はこの型を伸ばす**（例: Neovim＋LuaRocksの`luarocks.lua`、約370行。ZennのAIレビューで改善点なし）。構成は `## 結論`（完結した1ファイル＋読者が他所に足す2〜3行）→ `## 解説`（`###`を「つまみ1つ＝理由1つ」で分ける。`--lua-version 5.1`を忘れると何が起きるか、キャッシュした理由、旧版との差）→ `## 隣のツールと一緒に使う`（lazy.nvim、LSPのような、読者が次に踏むもの）→ `## 「〜でいいじゃん」`（1節だけ）→ `## 余談` → `## おわり`。調査の物語がないなら型Bにはしない
- 自分のコミットメッセージや過去の思い込みが、記事のための再現実験で再現しなかったら、実行したコマンドと出力ごと「再現しませんでした（未検証）」と書く。レビューはこれを長所として挙げた

## 型B: 問題解決の掘り下げ（150〜500行）

ある課題を、調査しながら解決した記録。
例: vue-i18n の辞書から配列を型安全に取る、`computed` が子コンポーネントから更新される、readonly が破れる、Happy のエラー報告。

```markdown
# タイトル（【型安全な実装】〜【の掘り下げ方】 のように前後に【】）

:::message
前提（Nuxt環境を想定、など）。あれば。
:::

# 結論

最終的なコード全部（辞書ファイル・ユーティリティ・使う側、のように複数ファイル）。
自分のPRやStackBlitzへのリンク。

# 問題

何がしたくて、何ができなかったか。
🙅 ❌ の例と 🙆 ⭕ の例を同じ形で並べる。

# 解決案

調べて見つかった案を引用（`[...](url)より引用`）。
「これは完成に近そうです！」「しかし`as any`を使うのは、あまりよくないです。」と評価。

# 解決策

調査の実況。
「では、適切な型とは何でしょうか。」
見た型定義をそのまま貼る → 「なんのこっちゃ？」 → 簡単な方に賭ける → 「ビンゴです！」

## 解

「材料は全てあつまりました。答えは次になります。」
コード。「やった！」

# 応用: 関数化する（任意）

# まとめ

結論のコードを**再掲**。「おつかれさまでした！」

- - - - -

（ライセンス・引用元・脚注）
```

- 主張の型は「発見の実況」。冒頭の結論は断定、本文は一緒に探す口調
- 崩しは「やった！」「ビンゴです！」程度に留める

## 型C: 自作ライブラリ・プラグイン紹介（150〜400行）

例: vim-fmap、luarrow、bakaup.vim、nvim-mado-scratch、expects。

```markdown
![（動作GIF）](...)

## はじめに

「〜、こんな経験はありませんか？」を2〜4個、鉤括弧のセリフで。
既存手段の限界を1段落。

- - -

「そこで僕は〜を開発しました。」
- [name - GitHub](url)

一文で何をするものか。

## 特徴

「全体と詳細はREADMEに書いてあるので、特に強調したい点だけ説明します。」
- [README.md - name](url)
- [docs - name](url)

### 推しポイント1
### 推しポイント2
（各ポイントはコード例1つ＋1〜3文。表は使わない）

## 実際にいただいた質問・反論への回答（あれば）

### Q1: 「〜でいいじゃん」
「確かに〜。しかし〜。」具体例で返す。

## 既存プラグインとの違い（あれば）

「〜は素晴らしいプラグインです。しかし敢えて言います。」

## READMEに書いていない、設計の話

### 初版は〜で、自分で自分を壊していた
（gitから掘り起こした初版を動かして、壊れた出力→直した出力を並べる。「だれだよ……僕だ。」はここ）
### 〜が2つでも、〜は1箇所
（抽象化の話。正規化したストリーム、共通の描画関数など）
### テストは、〜なしで走らせる
（テストの工夫。ハマったところを1〜2個）
### 〜にして、その日のうちに戻した
（やって戻したこと。1段落でいい）

## インストール方法

パッケージマネージャごとにコード。筆者の設定も載せる。

## まとめ

- **リポジトリ**: [...](url)
一行の締め。「よければ使ってね :metal::flushed::metal:」「もらえ！」「Happy Viming！」
```

- 自分の作ったものへの誇りは出すが、「劇的」「最強」の連打はしない。「最高になろう！」「最強にした」を1回使う程度
- 反論への回答セクションは、この型だけが持つ強み。Redditなどで実際に受けた指摘があれば必ず入れる。受けていなくても「〜でいいじゃん」を2〜3本、既存ツールの**実出力**を隣に並べて書く。既存ツールの方が優れている点も1行書く（ps-mem: 「`smem -p`のパーセント表示は`ps-mem`にはありません」）
- 「READMEに書いていない、設計の話」は、型Cで3本連続してZennのAIレビューに褒められた節。`###`は上の4種が定番だが、実際にあった分だけ書く。バグは**gitから初版を掘り起こして再現**する（`git show <fix>^:<path>`）。再現できないときだけ、コミットメッセージの引用＋「（未検証）」
- 実行例が本物のマシンを見せるツール（プロセス一覧、環境変数、ホームのファイル）は、サンドボックスの中でダミーを立てて撮り、冒頭の`:::message`で撮り方を申告する（SKILL.md 要件4）

## 型D: ガイドライン・概念解説（200〜600行）

例: HIKKY テストガイドライン、try式を関数で実装する、正規表現よりパーサー、generic-lens。

```markdown
# タイトル

本稿では〜について述べます。
対象読者:
- 〜がわかる
- 〜はよくわからない
（非対象者・既知とする概念・免責もここ）

# まとめ（先出し）または 結論

要点を箇条書き3つ、またはリンク集。

# 本編の章1

概念 → 具体例コード → 一文の確認（「原理は単純ですね。」）。
定義は太字で: 「境界とは、〜のことを指します。」
定義に迷う語は `:::message` か脚注で「ここでは〜と呼びます」。

## 応用: 〜
## おまけ: 〜

# 本編の章2
（「皆さん読むのが疲れてきたでしょうから、最後の〜を紹介して終わりにします！」のような読者への声かけ）

# まとめ

「おつかれさまでした！ あなたは本稿で、以下のことを学びました。」
- 箇条書き（章立てと同じ順）

# 付録（任意）

- - - - -
- - - - -

（脚注）
```

- 一人称は「筆者」、です・ます。崩しはほぼ0（「今見た通りね！」程度）
- 主張の型は「断定＋理由」。「筆者の答えとしては『〜！』です。」の形で意見を分ける
- 脚注を最も多く使う型。用語の別名・正常系/異常系のような分類名は脚注に

## 型E: 意見・ポエム（20〜80行）

例: Starをつけたほうがいいかもよ、ドキュメントコメントを書こう、Contributionsがすごい人は天才ではない。

```markdown
# 主張そのものをタイトルに（〜かもよ？ / 〜しよう！）

:::message
（用語の定義。必要なら）
:::

## 「反論1のセリフ」

前提（自分の立場・弱み）を正直に。「まず前提として、非常に悔しくも筆者は弱小OSSプログラマーで」
反論への返答を2〜3文。

## 「反論2のセリフ」

## 「反論3のセリフ」

主張を一文で再掲して終わる。「もし〜なら、〜した方がいいかもよ？」
```

- だ・である体で統一するか、です・ます体で統一するか、最初に決める（Star記事はだ・である、ドキュメントコメント記事はです・ます）
- 崩しは入れない。代わりに「僕はそのモノたちについての多くの情報が欲しいです！」のような率直な一文
- `# 序` / `# 終` の一文字見出しはこの型に合う

## 型を選ぶ基準

| 書きたいこと | 型 |
|---|---|
| 一つのハマりどころ・小技 | A |
| 調べて解決した過程がある | B |
| 自分の作ったものを知ってほしい | C |
| 読者に体系を教えたい | D |
| 読者の行動を変えたい | E |

迷ったらA。Aで書いてから長くなったらBに昇格する。
