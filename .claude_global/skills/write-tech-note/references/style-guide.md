このファイルは、`~/Repository/zenn-old/articles/` と `~/Repository/qiita-draft/` にある技術記事（2018〜2025年、約50本）を読んで抽出した、

**分析対象から除外したもの**: AI率が高いと本人が明記している記事（neosnippet移行 70%、VRChat写真 60%、git-worktree 30%）のAI部分、

## 1. 全体構造の癖

### 1-1. 結論ファースト（最重要）

タイトルの直後、前置きより先に `# 結論` / `## 結論` / `# 結` / `## まとめ` を置き、**コピペで使えるコード**と**動く環境へのリンク**を出す。
記事の半数以上がこの形。

````markdown
## 結論

下記のような感じ。

```vue
<script setup lang="ts">
const $assets = useAssets()
</script>
```
````

```markdown
# ZodIntersectionのプロパティの和型のうち、いらない型を`.and()`を使って除外する

- 全てはここにまとまっています: https://stackblitz.com/edit/...
- ↑実際に動かせます
```

- 結論に至る背景・調査は結論の**後**に書く（`# 問題` → `# 解決案` → `# 解決策`）
- 長い記事では、最後の `# まとめ` で**結論のコードをもう一度そのまま再掲**する（get-array, vue-export-value, ComputedRef）
- 「結論からお話します。」「単純だけど、そういうことです。」「たったこれだけです。」のような一文を結論の頭に置くことがある

### 1-2. 見出しは短く、ときどき一文字

- `# 序` / `# 終`、`# 起` / `# 承`、`# 結` / `# 解説` / `# 結`、`# 解`、`# おわり`
- 「起承転結」「序破急」を意識した見出しを使う。ただし全部は揃えず、`# 結` を先頭と末尾の2回置くことも多い
- 意見記事では見出しを**読者の反論のセリフ**にする
    - `## 「どうしてStarをつけた方がいいの？　私はStarをつける習慣はないよ」`
    - `## 「じゃあConventional Commits形式で書いてくれればいいじゃん」`
- ライブラリ紹介では `### ❓ Q1: 「メソッドチェーンでいいじゃん」` のように**実際に受けた反論**をQ&A化する
- 末尾の蛇足は `# 余談` / `# おまけ` / `# 蛇足` / `## おまけ: 〜` / `## 応用: 〜`

### 1-3. 対象読者・前提の明示

本編の前に、箇条書きで読者を絞る。

```markdown
対象読者:
- 実際にテストを実装してみようと思ったけど、**とっかかりがつかめなかった**
- **テストの概要はわかった**（[単体テストと結合テストガイドライン](...)を読んだ）
```

```markdown
この記事の想定読者レベル

- Haskellに入門済み
- Haskellの文化には詳しくない
```

```markdown
本稿は以下の概念を既知とします。

- [lens: Lenses, Folds and Traversals](...)
- `DefaultSignatures`
```

- 「この記事の非対象者」も書く（why-parser）
- 主題の範囲を明示して、扱わないことを宣言する: 「本稿の主題は「静的型付き下でreadonlyの制約を破る」であり、実行時（例えば下記コード）を考慮して制約を破ることは目標としていません。（それは簡単すぎるので！）」
- 用語の使い方を先に断る: `## 用語の乱用` セクションで「この記事では以降、わかりやすさを重視するため、慣習・口語での説明にならい、以下の用語の乱用を行います。」

### 1-4. 区切り線と Zenn/Qiita 記法

- 水平線は `- - -` か `- - - - -`（スペース入り）。`---` は使わない
- 大きな区切り（付録の前など）は `- - - - -` を2行連続で置く
- Zenn:
    - `:::message` … 前提・注意・「余談ですが」・AI率の申告
    - `:::details タイトル` … 追記、ソースを読んだ感想、ライセンス、完全な余談
    - 追記は記事の**最上部**に `:::details 追記: ...` で置く（ComputedRef, VRChat）
- Qiita:
    - `<details><summary>...</summary><div>` … 結論のコード例を畳む
    - `:::note info`
    - 絵文字はショートコード `:tada:` `:sparkles:` `:point_down:` `:dog2:` `:thinking:` `:sob:`
- 画像は `![](url)` でaltなしが多い。GIFで動作を見せる
- 自分のリポジトリへのリンクはコミットハッシュ付きの行リンク（`.../blob/861ebefc.../list.lua#L202`）。URLを裸で1行に置いてカード化させることもある

### 1-5. 脚注

- 識別子は**意味のあるkebab-case**: `[^what-is-combinator]` `[^do-not-use-power-shell]` `[^e2e-encrypt]` `[^by-PBT]` `[^testing-trophy]`
- 番号（`[^1]`）は使わない
- 脚注本文は、その段落の直後に置くことが多い（記事末尾にまとめることもある）
- 用途: 用語の定義、細かすぎる注意、「目ざとい方は気づかれたかもしれませんが」系のペダントリー、参照リンク
- 本文を軽く保つために脚注へ逃がす。本文に `※` を使うこともある（「※ 本稿ではこれらをクラウドストレージ事業者と呼称します」）

## 2. コードの見せ方

### 2-1. ファイル名付きフェンスとシェルセッション

````markdown
```vue:A.vue
```typescript:utils/i18n.ts
```json:ja.json
```shell-session
$ expects "$x" to_be 10 && echo Success
Success
```
````

- シェルは必ず `shell-session` で `$ ` プロンプト付き、**出力も一緒に載せる**
- 出力がないことを示すときは `（無）`
- `diff` フェンスで Before/After を見せる
- 実プロジェクトのコードを「擬似コード（実商業プロジェクトの一部）でお送りします。」と断って載せる

### 2-2. コメントで語る

コードコメントに感情と指摘を書き、本文の説明を減らす。

```typescript
const assetsComp = useAssets() // かっこわるい

proxy.value += 10 // typecheck error ！
(e: 'update:modelValue', value: U): void  // 間違ってvalueがTでなくUになっている
// これだよ
// ↑ここ重要！
// 評価されないから恥ずかしくないもん！
-- vvv ここは絶対に通らないよ！もしここを通ったら木の下に埋めてもらっても構わないよ！
```

### 2-3. 良い例・悪い例の対

- 🙅 ❌ / 🙆 ⭕ を段落の頭に置いて、同じ構成のコードを2回並べる（get-array）
- Qiitaでは `:point_down: :x:` / `:o:`
- 「**正しい↓** … **正しい↑**」で挟む
- 悪い例には `// !! ここでは個別にアイテムを取得したくない`、良い例には `// !! 一度に配列を取得している`
- 問題の位置を **`ここ`** と太字にして指す:
    ```typescript
    const emit = defineEmits<{
      (e: 'update:modelValue', value: ここ): void
    }>()
    ```

### 2-4. 第一原理への還元

結論の理由を、型の計算式や意味論に落として示す。

```
{ a: number | null } & { a: number }
= { a: (number | null) & number }
= { a: (number & number) | (null & number) }
= { a: number | never }
= { a: number }
```

- 「実はそれはそうで、これはzodスキーマに限った話ではなく、TypeScriptの素の型でそうなっています。」
- 「よく考えたら当たり前で、〜は関数でいうシャローコピーの渡しになるからです。」
- Kotlin / Haskell の対応する概念と比較する（`MutableList`と`List`、`catch`と`handle`）
- 図はASCIIで:
    ```
               decode関数
           I  ----------->  (A | Errors)
    ```

## 3. 文体・口調

### 3-1. 人称

- 一人称: **「僕」**が基本。ガイドライン・意見記事では**「筆者」**。「私」はまれ
- 会社は「弊社」「某所」「弊チーム」「弊部」。チームを含めるとき「我々」「私達」
- 読者は「あなた」「皆さん」「〜な全人類」
- **1記事内で一人称を混ぜない**（本人の記事では混ざっていない）

### 3-2. 基本は です・ます、ところどころで崩す

地の文は丁寧体。ただし**独立した1行**で突然口語・タメ口・叫びが入る。これが最大の特徴。

```
わかる～。
こいつなんでも食いやがる…。
なんも信じられん。
許せん。
ヨシ！
やった！
はい通った！
ビンゴです！
うんうん。
あれ？
そう。
勝ち申したな！！！！！！！！
`.every`！　お前型ガードしてくれよ！！
おまえ`-eq`オプションなんてないだろうが！！！
`printf`しか勝たん。
需要あるのか？
なんで……？？ 🤔
```

- 崩しは**短く、行を独立させ、説明段落の中には入れない**
- 頻度は記事の長さに応じて2〜5回程度。小ネタ記事では多め、ガイドラインではほぼゼロ
- 意見記事（Star、Poem）は全文 **だ・である** で書く。この場合は崩しを混ぜない

### 3-3. 発見の実況

調べた過程を、読者と一緒に見ているように書く。

- 「では、適切な型とは何でしょうか。ここまできたら、lspをガンガン使って、実地調査をしていきましょう。」
- 「なんのこっちゃ？ 手動簡約するのはめっちゃがんばればいけそうですが、今回は`i18n.rt`の型定義がもっと簡単であることに望みをかけて、そちらを見てみましょう。」
- 「材料は全てあつまりました。答えは次になります。」
- 「勘のいい人は気づいてしまったかもしれません。」
- 「……えっ？ なんかいきなり趣が違くない？」
- 「聡い読者の方は気づいたかもしれませんが」
- 「ごめんなさい**というのは嘘です**。」（一度言ったことをひっくり返す構成）

### 3-4. 正直な断り書き

できていないこと・確認していないことを隠さない。

- 「間違っていたら教えてください。」
- 「（ソースを読んだ感想です）」
- 「（追記なので、以下は実働を確認しておりません。失礼します！）」
- 「jqわかんないので、手動でjsonの形に直します。ここのやり方わかる人、この記事にPRください！」
- 「TODOは残っています。TODOを解消できた人は、コメントで教えてください！」
- 「（-O1では。-O1以外だとどうなんだろ。）」
- 「うちの環境だけ？」
- 「まあここでdocker関連のエラーが出ても、見過ごしていいと思えるならOK」

### 3-5. 主張の仕方

- 断定して、直後に理由を1〜2文で付ける。理由は「型が壊れる」「静的に検証できなくなる」のような**具体的な損失**
    - 「しかし`as any`を使うのは、あまりよくないです。`any`を使用すると、そのコードが正しいのか静的に検証できなくなるからです。」
- 強い意見は強い言葉で一度だけ。繰り返して煽らない
    - 「タイムアウトは発生させるな！ **自動テストは必ず完遂させろ！** 絶対だぞ！」
    - 「絶対unsafeコ□していこうな。」
- 一般論より「僕はこう考える」「筆者の私感による説明になります」
- 反論を先回りして見出しにし、一つずつ返す（luarrow Q1〜Q4、Star記事）
- 「〜かもしれませんが」で譲ってから「それは一貫性があるということだと思ったので、今はこれを採用しています。」と結ぶ

### 3-6. ユーモアのパターン

- **自虐オチ**: 「だれだよこんなコード書いたの。`git blame`してやる。……僕だ。糸冬」
- **ツールの擬人化**: 「mochaちゃんに『は？　ブラウザビルドされたFirebase？　知らないわ。私はnode派なの。』と言われてしましました。」「GitHub氏、その設計でよかったんか？」「GitHub Copilot Chatたん～～～！！！」
- **言語へのツッコミ**: 「TypeScript が型をつけてくれる？ 否。私達が "TypeScript に" 型をつけて回るのだ。」
- **ネットミーム**: 「〜しか勝たん」「ありよりのあり」「ムダムダムダァ」「オラオラオラ」「古事記にも書かれています」「マナー違反ですよ！！！」
- **括弧内のぼやき**: 「（なんでキーマッピングソフトでウィンドウマネージャ作った？）」「（それは簡単すぎるので！）」
- 記号: 「><」「＞＜」「:3」「🐕」（犬が自分のアイコン）
- 文の締めが「。」なしで「＞＜」「！」「……」で終わることがある

### 3-7. 締め方

短く、勢いで終わる。「この記事が皆さんの〜になれば幸いです」型の定型は**使わない**（AI草稿にしか出てこない）。

```

```

- `# おわり` セクションの本文が「おわり」の一語だけ、というのもある
- 長い解説記事では「あなたは本稿で、以下のことを学びました。」＋箇条書きで締める

### 3-8. 文レベルの癖

- 一文一行。「、」で改行して1文を2〜4行に割ることもある（詩のように）
- 三点リーダーは「……」（2つ）か「…」。「！？」「！！！」を使う
- 全角括弧の中に補足を入れ、括弧だけで1段落にする。長い補足は `（` と `）` を独立行にして中身を複数行書く
- 「そう。」「はい。」「うんうん。」「あれ？」の一語文
- 「〜ですよね」「〜ますよね！」で同意を求める
- 「〜と思います」「〜かなと思います」「〜っぽい」「〜な気がします」で確信度を下げる
- 「ちなみに」「余談ですが」「要は」「つまるところ」「つまり」「そう、」で接続
- 「やんごとなき理由で」「礼節のあるHaskell文化にならい」のような、少し古風・大仰な言い回し
- 全角コロン「：」は使わない。半角「:」（「対象読者:」「引用元:」「例:」）
- 引用元は `- [タイトル - サイト名](URL)` の箇条書き、または `[...](...)より引用。`

## 5. うまいところ（まねすべき長所）

1. **10秒で使える**: 結論のコード＋StackBlitz＋自分のPRリンクが冒頭にある。読者は本文を読まなくても持ち帰れる
2. **調査の再現性**: 「どの型定義を見て、どこで諦めて、どっちに賭けたか」まで書くので、読者が同じ手順を別の問題に使える
3. **スコープの正直さ**: 扱わないこと・未検証のこと・残っているバグを冒頭または脚注で先に言う。信頼できる
4. **対比の明快さ**: 悪い例と良い例が同じ形で並び、差分がコメント1行で指されている
5. **理由が根に届く**: 「なぜそうなるか」を型の計算や言語仕様まで降りて示す。他言語との比較で直感を補強する
6. **脚注で本文を軽く保つ**: 細かい正確さを捨てず、本筋の読みやすさも捨てない
7. **反論の先取り**: 想定される「〜でいいじゃん」を見出しにして潰す。意見記事はこれだけで構成できる
8. **緩急**: 丁寧な説明の合間に一行の叫びや自虐が入り、読み疲れない
9. **自分の失敗を教材にする**: 「僕だ。」で終わる記事や、自分のひどい正規表現を晒す記事。失敗は語るより**再現して見せる**。初版をgitから掘り起こして、壊れた出力と直った出力を並べる（ps-mem: `smem`版が改行入りの引数で一番大きいプロセスを黙って落とす様子を、3ブロックで再現した）
10. **メタ情報の開示**: AI率、ライセンス、会社との関係の免責、を明記する習慣がすでにある。実行例の撮り方（サンドボックス、ダミープロセス）も、冒頭の`:::message`で申告する
11. **READMEの外側を書く**: 自作ツール紹介では、READMEに書いてある使い方を繰り返さず、命名規則の理由・テストの工夫・設計の流儀のような「作った人にしか書けないこと」を載せる。AIと書いた際の失敗（`to_be`が`-eq`だった話）を包み隠さず書いた節が、記事の信頼性と面白さの両方を上げた。「やって、その日のうちに戻した」ことも1段落で書く

（7・9・11は、2026-09-06のZenn AIレビュー4本（型C: `expects`、bash-toys、`ps-mem` / 型A: Neovim＋LuaRocks）が全部「改善点: 特にありません」で、そのたびに「良い点」として挙がったもの。レビューの全文と、褒められた点がどのルールに対応するかは `review-log.md` にある。型Cでは「〜でいいじゃん」の比較節と、正直な失敗談・経緯の節が、レビューで一番評価される。型Aでは、完結した1ファイル、動かして初めてわかる知見、隣のツール、そして「未検証」を隠さないこと。未検証を隠さないことは、減点ではなく加点になる）

## 6. まねしてはいけないもの（AI草稿にだけ出てくる癖）

以下は本人の文体ではない。生成時に一つも出さない。

- 見出しの絵文字（`## 🚀 はじめに`）、`✅` `❌` の箇条書き、`○△×` の比較表
- 「劇的に」「格段に」「革新的」「圧倒的に」「間違いなしです」「〜を実現します」「〜に最適」の連打
- 「**課題**：〜 **解決策**：〜 **結果**：〜」のテンプレ
- 「この記事では〜について解説します。」「〜の方の参考になれば幸いです。」「Happy Vimming! 🎉」
- 「特にこんな方におすすめ」の箇条書きが2回以上出る
- 「今すぐ試してみませんか？」「ぜひ一度試してみてください！」の反復
- 全角コロン「：」で文を終えてコードブロックにつなぐ（「以下のコマンドです：」）
- 太字の乱用（1段落に3つ以上）
- 統計サマリー（「新機能追加: 3つ」「バグ修正: 5つ」）
- Claude Codeキャラクターの口調: 「〜なのです」「〜ますです」「♪」「わたし」「あいやくん」「〜ですです」「〜かなって」。**一つでも出たら失敗**

## 7. 一貫性のルール

記事を書き始める前に決めて、最後まで守る。

| 項目 | 選択肢 | 既定 |
|---|---|---|
| 一人称 | 僕 / 筆者 / 私 | 僕（ガイドライン・意見記事は筆者） |
| 文体 | です・ます / だ・である | です・ます（意見記事のみ だ・である） |
| 崩しの頻度 | 0回 / 2〜5回 | 記事の種類で決める（§3-2）。決めた回数を超えない |
| 主張の型 | 断定＋理由 / 発見の実況 | 記事の種類で決める。途中で切り替えない |

- 冒頭で強く断定したなら、まとめで「〜かもしれません」に弱めない。逆も同じ
- 「余談」「おまけ」「蛇足」のうち一つの語を使い続ける
